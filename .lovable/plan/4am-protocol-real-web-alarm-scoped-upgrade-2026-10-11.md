# 4AM Protocol — real web alarm, scoped upgrade

## Scope and confirmed findings
- Change only the wake alarm experience and the integrations needed to make it work. Preserve other screens, layouts, themes, navigation, auth, rewards and features. No publishing without separate approval.
- Reuse `WakeProtocol`, existing ringtone assets, the `alarms`, `alarm_sessions`, `quiz_questions`, `task_completions`, `profiles`, `score_events` and `coin_transactions` structures, plus `CoinBadge` and the existing serialized completion-award helper.
- Source inspection confirms that scheduling/countdown currently use the device clock and hour-only tiers. Save currently marks the local plan armed before the account save finishes. `WakeVerify` supplies answers in client code and stops audio before the completion request finishes.
- Live database inspection confirms that wake completion currently accepts a slot without server question evidence, pays up to 10 capped coins using a UTC day, and updates wake sessions/tasks/streaks. The completion helper currently supports Zen, Contract and Top 3 only. These wake-specific paths need secured integration, not a second reward system.
- The existing database has 15 science questions, not 400. The current question SELECT policy exposes active rows; the new wake bank must keep answer keys private without disrupting unrelated quizzes.
- Live inspection found no alarm-event/push-subscription tables or admin-role helper/table. `pg_cron` is installed; `pg_net` is not. No VAPID or alarm-job secret names are currently configured.

## 1. Saved settings and truthful readiness
- Keep the current tier cards, Sleep Goal, Wake Reminder, Evening Plan, Milestone Journey and both existing actions. Add only the requested repeat-daily switch, three math difficulties, compact readiness/test area and Overnight Mode action within the protocol.
- Save exact 24-hour sleep/wake times, selected existing sound, Math/Science, difficulty, alarm on/off and repeat daily to the existing per-user alarm. Preserve additional existing sound choices rather than removing assets/options.
- Use the stored IANA timezone, defaulting to the existing `Asia/Kolkata` setting. Do not weaken the protected reward-timezone rule or introduce a client-controlled reward day.
- Compute and store the next UTC occurrence on the server; return server time, timezone, next fire time and readiness state. Countdown uses that saved occurrence and a server-synchronized monotonic clock, not an unsaved tier selection.
- DST policy: a missing spring-forward time moves to the first valid instant after the gap; an ambiguous fall-back time uses its first occurrence and never fires twice that local day. Recompute after save, solve, authorized timezone change and DST transitions, using indexed pending occurrences rather than scanning users.
- Saving must report separate outcomes: settings saved, push registered, or Overnight Mode ready. Never say the alarm is armed while disabled or while no working delivery layer is ready. A failure in push registration must not erase successfully saved settings.
- Show live permission, push subscription, iOS installation and Overnight Mode status, plus a volume reminder; hardware volume cannot be measured. Include the exact warning: “Browser alarms can't be guaranteed on every phone. Keep a backup alarm until your test works.”

## 2. Overnight Mode and persistent ringing
- Introduce `AlarmScheduler` and `WebAlarmScheduler`; retire the old local-only wake trigger from the active wake flow. Keep native plugin support as a future adapter, not a new native guarantee.
- A user tap primes WebAudio and requests Screen Wake Lock. Display a dim clock with “Keep this screen open and plug in your phone”. Reacquire locks when possible and show failures/lost readiness honestly.
- At the server-synchronized due time, atomically claim the event as ringing, loop the selected audio, ramp to maximum browser output within 20 seconds and vibrate where supported. Prime a synthesized fallback during the user tap and switch to it on media failure.
- Add the authenticated `/alarm` page, using the existing visual vocabulary and solve controls. No close, snooze, skip or in-app back action while unsolved. A wake-only observer restores a ringing alarm on app open, reload, focus and attempted in-app navigation, without replacing auth or changing other page layouts.
- Keep authoritative ringing state until a verified solve. Exhausting push retries or the reward deadline must not silently stop an unsolved alarm. Expire cancelled/superseded scheduled events, not an actively ringing event to bypass the gate.
- `I’M AWAKE` opens/resumes the server question flow; it cannot award or mark completion by itself. Audio stops only after the server confirms solved. If offline, keep ringing and show that verification needs a connection.

## 3. Server questions and solve gate

- Add at least 400 reviewed science questions across physics, chemistry, biology, earth science and astronomy. Each has four options, one unambiguous answer, a short explanation and a factual source/attribution record. Document factual review and reject ambiguous or unsupported entries; do not label generated content “verified” without review.
- Generate Math server-side using tested arithmetic, multi-step, percentage, algebra and sequence templates across three difficulties. Validate numeric submissions on the server.

Persist per-user content hashes and cycle history; exclude repeats until the bank is exhausted, then reshuffle. Track every issued question, including replacements after wrong answers.

- Serialize challenge state and version submissions so parallel tabs, stale answers, duplicate requests and forged solved flags cannot bypass the gate. Bound rapid submissions without freezing the ringing experience.
- Secure all existing wake-completion entry points, including manual/Profile/scheduled paths and legacy RPCs targeting the Wake Protocol alarm. Keep unrelated alarm and task behavior unchanged.

## 4. Completion and rewards
- Confirmed reward interpretation: **04:00–04:59 = 10 coins; 05:00–05:59 = 7; 06:00–06:59 = 5; 07:00–07:59 = 3; all other times = 0.** Alarm functionality works at every time.
- Derive tier from the saved wake time, never a client-provided slot or reward. Snapshot schedule, timezone and eligibility timestamps on each event.
- Eligible reward requires the alarm schedule to have been saved at least two hours before first ring and the final verified solve to occur no more than 30 minutes after first ring. Test events are always ineligible. Changes to wake scheduling reset the relevant eligibility timestamp; question/sound preferences may change until ringing without moving the schedule.
- Extend the existing completion config/helper with one daily wake source and variable server-derived tier amount. Reuse ledger uniqueness, profile locking and cap-exemption pattern; leave Zen, Contract, Top 3 and the 50-coin cap for other activities unchanged.
- In one transaction: verify solved evidence, finalize the event, write one eligible ledger award, update balance and existing wake completion/streak/task/XP-score behavior exactly once, then schedule the next daily occurrence. Prevent alternate legacy calls from awarding again.
- Preserve existing XP tier values 10/7/5/3 and milestone rules; do not add a parallel XP system or double-count XP already represented by existing score logic. Confirm the existing accounting path before wiring it.
- A late, fresh, outside-window, already-claimed or test solve still stops the alarm, returns zero coins and displays the exact reason. Only server-confirmed positive awards animate `CoinBadge`; no fake “+”.

## 5. Push backup and scale
- Add only the missing operational records: alarm occurrences, private push subscriptions, question-use/challenge history, push outbox and delivery logs. Link events to the existing alarm and session rather than creating duplicate settings/completion tables.
- Add `(status, scheduled_for)` and a scheduled-only partial index, unique occurrence keys and indexed retry/lease deadlines. Guard server-owned event status, timestamps, challenge progress and awards against direct client writes.
- Add a narrowly scoped service worker and web-app manifest for install/push support; no generic offline caching of private pages, auth or answers. Push taps open `/alarm`; notifications contain no answer keys or unnecessary personal data.
- Use a Worker-compatible WebCrypto/fetch Web Push implementation. Securely provision VAPID credentials and a private job-authentication secret after approval; expose only the VAPID public key. Public callback handlers must verify the private job credential before privileged work.
- One per-minute coordinator processes indexed due events in batches of 500 using `FOR UPDATE SKIP LOCKED`, commits ringing/outbox transitions, then wakes bounded delivery processors. Never hold row locks while contacting push providers or let slow endpoints block scheduling.
- Delivery processors use leases/fencing, attempt uniqueness, timeouts and concurrency of at most six outbound requests per invocation. Scale through bounded independent invocations, not an oversized `Promise.all`. Retry transient failures with exponential backoff; remove 404/410 subscriptions automatically.
- Re-notify ringing events at 60-second intervals, with at most 30 notification rounds and stable notification tags/event IDs. Check solved state before each dispatch and drop obsolete queued rounds.
- Prevent duplicate event claims and duplicate outbox jobs. External push delivery is inherently at-least-once: an ambiguous network timeout may cause a retry after provider acceptance. Deduplicate on the receiving service worker and report this limitation rather than promising impossible transport-level exactly-once delivery.
- The one-minute check runs **1,440 times daily**, may increase Cloud costs and can introduce roughly 60 seconds of scheduling delay plus queue/provider/device delay. Overnight Mode gives the closest available in-app timing. Arm scheduling only while pending/future alarm work exists and remove the schedule when drained; recurring daily alarms naturally keep it active.
- Add a private aggregate log/report for daily due, queued, provider-accepted, failed and solved counts. Provider acceptance is not proof the phone displayed or sounded an alarm. Use a protected separate role table if an admin UI is needed; grant no admin role automatically. The initial implementation can remain a private backend log without adding another user-facing screen.

## Known web limits
Browsers cannot prevent tab/app closure, hardware muting, OS termination or notification suppression. Wake Lock, vibration, audio and push vary by browser and device; fallback synthesis cannot defeat an OS-level audio block. iOS push requires an installed Home Screen app on iOS 16.4+ and permission. Push notifications cannot remotely force a page open or guarantee a looping alarm sound. The solve gate controls app actions and rewards, not the phone's power/back/mute controls. Keep the backup-alarm warning visible.
